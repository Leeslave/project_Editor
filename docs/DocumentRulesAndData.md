# Document 공통 규칙과 데이터 계약 (002)

작성: 2026-09-09. 구현 범위: 독립 C# DTO, 콘텐츠 참조 검증, 플레이 사본 생성, 문자열 비교, 영속 키 생성. 기존 씬의 게임 동작 전환은 003–006에서 수행한다. 테스트·빌드·Unity 실행은 수행하지 않았다.

## 근거와 결정 수준

기획 기준은 `tasks/게임_Editor_진술_대조_및_문서_조작_미니게임_기획서(1)_(1).pdf` v0.1, pp.2–11이다. 2026-09-09 전체 11쪽의 텍스트를 확인했다. 아래 기록·잠금·비교·열람 단위는 초안의 빈 부분을 채우기 위한 **이번 구현 결정**이며 원문에서 확정된 수치가 아니다.

평판 증감량, 극비 해금 AND/OR·같은 날/누적, 분기 임계값·연결 일차는 **미정**이다. `DocumentPolicy`의 nullable 수치와 `Unspecified`를 사용한다. 0을 미정의 대체값으로 사용하지 않는다. `PrerequisiteWorkCodes`는 확정 시 Dodge/Maze 등 실제 코드를 명시하며 빈 목록을 자동 해금으로 해석하지 않는다. 006은 정책 미설정 시 해금·평판 적용을 확정해 실행하지 않고 구성 오류를 반환해야 한다. 일반 모드에는 극비 해금 정책이 필요 없다.

## 데이터 경계

구현: `Assets/Scripts/Common_Documents/DocumentContracts.cs`, namespace `EditorGame.Documents`. 기존 전역 `Docs`, `Instruction`, `PeopleIndex` 및 Unity 직렬화와 이름이 충돌하지 않는다.

| 계약 | 소유 정보 | 변경 시점 |
| --- | --- | --- |
| DocumentAssignment | 모드, stage, 대상 날짜, 원본 인물·문서·정답 쌍·수정 지시·정책 | 콘텐츠 제작 시에만 |
| DocumentPlayState | 업무 실행 ID, 수정 인물 사본, 조사·기록·열람·평판 사건, 단계 | Working 동안 |
| DocumentSubmission | 업무 코드·stage·날짜, 성공 여부, 제출 스냅샷·필드별 결과 | 제출 시 생성 후 불변 취급 |

DTO는 JSON 저장 경계이므로 공개 필드를 사용한다. 불변성은 타입 자체가 강제하지 않는다. 후속 컨트롤러는 원본을 내부 보관하고 UI에는 사본 또는 읽기 전용 뷰를 전달하며, 제출 시 `DocumentContract.Copy(state)`로 깊은 복사해야 한다. `Begin`은 콘텐츠를 검증한 뒤 인물의 다섯 필드를 모두 깊은 복사하고 새 조사 목록을 만든다. `Copy`는 Unity 객체 없이 JSON으로 복사하며 `$type`을 사용하지 않는다.

`DocumentAssignment.Id`는 제작자가 부여한 업무 콘텐츠 ID다. 모드별 WorkCode는 `StatementCheck → Document`, `Forgery → SecureDocument`이고 두 모드의 씬은 Document다. Stage는 현재 `IWorkService.GetStage(WorkCode)`와 연결한다. `TargetDateId`는 문서상의 날짜 식별자이며 플레이 날짜나 stage와 동일하다고 가정하지 않는다. 샘플의 `example-day-3`은 출시 일차 편성값이 아니다.

`WorkInstanceId`는 006/007이 세이브 분기·플레이 날짜·업무 슬롯·콘텐츠 ID로 구성해 제공한다. 재진입할 때 임의 GUID를 새로 만들어서는 안 된다. 같은 실행의 평판 중복 방지 키가 달라지기 때문이다. 표시 이름·리스트 인덱스·변경된 Name은 식별자가 아니다. 인물·문서·문장·정답·지시 ID는 콘텐츠 내에서 유일하며 정렬/텍스트 수정 시 유지한다. 열람 문서는 PersonId와 DateId를 갖는다. `Validate`가 중복 ID, 끊어진 참조, 다른 날짜/인물 정답 쌍, 잘못된 모드, 중복 필드 지시를 거부한다.

## 상태 전이와 재진입

`Working → Submitted → Applied` 순서이며 되돌아가는 전이는 없다. Submitted 전환 시 수정/기록 입력을 잠그고 스냅샷과 평가 결과를 만든다. 오답이나 미수정이어도 제출은 성립한다. `Successful`은 업무 완료 여부와 별개다. Applied는 006에서 평판 사건과 업무 완료를 한 번 반영했다는 의미다.

일반 모드는 모든 지정 대상의 Completed가 참이어야 제출할 수 있다. 극비 모드는 Working이면 수정 여부와 무관하게 제출할 수 있다. 실제 명령 처리·버튼 연결·채점은 004/005가 이 계약에 맞춰 구현한다. DTO의 Phase 필드를 UI에서 직접 변경하지 않는다.

창 닫기/재열람은 현재 세션의 수정값·기록·조사완료·열람 이력을 보존한다. 선택 패널 두 개와 창 좌표는 UI 임시 상태로, 취소 시 선택만 지운다. 조사완료는 한 대상의 기록을 잠그며 재열람은 허용하되 추가 기록/취소/수정은 막는다. 최종 제출 이후에는 결과만 읽는다.

같은 미완료 업무에 씬 재진입하면 동일 WorkInstanceId의 플레이 상태를 복원한다. 이미 생성/적용된 평판 사건을 버리고 `Begin`으로 재시작하지 않는다. 새 업무 실행에서만 `Begin`을 호출한다. 다음 날은 새 실행 ID와 상태를 쓰되 과거 적용 이력은 보존한다. 메모리 보관은 006, 저장/불러오기와 분기별 격리는 007의 책임이다.

## 진술 대조 결정

- 기록 1건은 선택한 진술 1개와 행동 1개가 모순이라는 신고다. 정답 쌍에 없으면 오판이며, 오판도 최소 1건 조건에 포함된다. 별도의 '일치 신고' 선택지는 없다.
- 정답은 명시된 ID 쌍으로 판정한다. 시간 차이·문장 유사도로 자동 추론하지 않는다. 한 대상에 여러 AnswerPair를 둘 수 있다.
- 같은 두 문장의 재기록은 새 기록/사건을 만들지 않는다. 같은 진술에 다른 행동을 묶은 기록은 별개다. 정답 0개인 지정 대상은 현재 규칙에서 제외한다. 최소 1건 신고를 강제하면서 정답 없는 대상에게 오판을 강요하지 않기 위해서다.
- 조사완료는 기록 1건 이상일 때 가능하다. 완료 순간 발견하지 않은 정답 ID를 MissingAnswerIds에 확정하고 정답 쌍마다 누락 사건을 생성한다. 재완료 요청은 아무것도 추가하지 않는다.
- 지정 인물 + 지정 날짜 문서의 재열람은 무료다. 다른 인물 또는 다른 날짜는 열람을 허용하고 위반 사건을 만든다. 두 조건이 모두 어긋나도 한 열람당 1건이다.
- 열람 단위는 **닫힌 파일을 여는 행위 1회**다. 열린 창의 포커스 이동, 스크롤, 재배치는 열람으로 세지 않는다. 닫은 비지정 파일을 다시 열면 새 열람 ID와 사건을 만든다. 진술·행동 파일은 각각 별도 열람이다.

## 문서 조작 결정

초상화는 PortraitKey로 참조하는 표시 자산이며 수정 대상이 아니다. Name/Age/Sex/Country/Job은 모두 문자열이다. 나이도 숫자로 강제 변환하지 않으며 국가/직업 enum에 제한하지 않는다. PersonId는 Name 변경과 무관하게 유지된다.

입력 중에는 정답을 판정하거나 자동 교정하지 않는다. 제출 시 `SameText`로 비교한다. Unicode NFC 정규화만 수행하고 앞뒤/중간 공백, 대소문자, 문장부호는 구분한다. null 입력은 빈 문자열로 취급한다. IME 조합 완료·포커스 이동·닫기 때 최종값을 사본에 반영하는 책임은 005에 있다.

필드별 결과는 원본/제출값/기대값을 보존한다. 지정 필드의 기대값은 지시 문자열, 비지정 필드는 원본이다. 목표와 같으면 CorrectEdit, 원본 그대로인 지정 필드는 UnchangedTarget, 원본과도 목표와도 다른 값은 IncorrectEdit, 비지정 필드 변경은 UnrequestedEdit로 분류한다. 사람 단위 부분 수정은 필드별 결과의 조합으로 표시한다. '오타'의 의도를 추론하지 않고 목표 불일치로 취급한다.

전혀 수정하지 않은 지정 인물은 인물당 UnchangedTarget 큰 패널티 사건 1건으로 집계한다. 이 경우 같은 인물의 필드별 미수정 패널티를 추가하지 않는다. 부분 수정은 미수정 지정 필드마다 일반 UnchangedTarget 사건을 만든다. 인물 단위와 필드 단위의 수치는 `ReputationUnit.Person / Field`로 구분해 별도 설정한다. 규칙 조회 키는 Reason + Timing + Unit이다. 지시값이 원본과 동일한 필드는 미수정 패널티 대상이 아니며 007에서 실제 변경 지시만 편성한다.

## 평판 사건과 중복 방지

| 사유 | 생성/적용 시점 | 사건 키의 대상 부분 |
| --- | --- | --- |
| CorrectPair / IncorrectPair | 기록 즉시 | 진술 ID + 행동 ID |
| UnauthorizedView | 파일 열람 즉시 | 지속 증가하는 열람 ID |
| MissingPair | 조사완료 즉시 | 정답 쌍 ID |
| CorrectEdit / IncorrectEdit / UnchangedTarget / UnrequestedEdit | 극비 제출 시 | 인물 ID + 필드 또는 전체 인물 |

모든 키는 `DocumentContract.Key(WorkInstanceId, reason, subject...)`로 만든다. 문자열 길이 접두어로 구분자 충돌을 막는다. 사건의 수치는 생성 시 확정하여 저장하고 재열람/제출 시 현재 설정으로 다시 계산하지 않는다. 미정 Delta는 적용 금지다. 제출 스냅샷은 이미 적용된 사건도 포함하지만 최종 총점을 평판에 다시 더하지 않는다.

006/007은 영속 applied-event-ID 집합과 applied-work-ID 집합을 보관한다. 평판 갱신과 사건 키 기록을 함께 저장하여 중간 실패 후 재개해도 중복되지 않도록 한다. DTO의 Applied 상태만으로 영속 중복 방지가 구현되었다고 간주하지 않는다. 설정되지 않은 정책은 아직 실제 게임에 연결하지 않는다.

## 기존 기능의 유지와 이전

`DB_M.Start`는 기존 `Instruction.InfoInst/NewsInst/DocsInst`에서 정답을 구성한다. `InfChange.ChangeInf`와 저장 코드는 belong/part/curFace와 enum 드래그를 실제 사용하며 `ToDoList_N`과 `DB_M.EvaluateWork`는 뉴스 지시·채점을 사용한다. 따라서 002에서 해당 필드/클래스/씬 참조를 삭제하지 않는다.

새 두 모드에는 뉴스 수정, 소속·부서 전용 필드, 얼굴 교체를 이전하지 않는다. 복합 부서·직책은 Job 문자열로 표현한다. 기존 직렬화 데이터는 레거시 흐름에서 유지한다. 기존 Name 기반 검색과 배열 인덱스를 런타임에서 새 ID로 자동 승격하지 않는다. 007에서 콘텐츠 제작 시 명시적으로 안정적인 ID를 부여한다. 현재 DB_M의 통합 로딩·채점을 새 모델에 억지로 연결하지 않으며 003–005에서 새 로더/세션/UI를 연결하고 006에서 제출 서비스를 연결한다.

## 후속 작업 계약

- 003: 모드/WorkCode/Stage/TargetDateId에 맞는 콘텐츠 선택, 창 열람 이벤트 및 수정 사본 뷰, 일반/극비 공통 패널.
- 004: 위 기록/완료 잠금/재열람 단위, 복수 정답·누락 채점, 일반 제출 스냅샷.
- 005: 다섯 문자열 직접 입력, NFC 정확 비교, 필드별 결과와 무수정 인물 집계, 극비 제출 스냅샷.
- 006: 확정된 해금/평판 설정, 세션 보관, 사건 단위 적용·업무 완료·결과 표시. 기존 006 문서의 완료 코드 고정 문제는 001에서 이미 수정되었으므로 회귀시키지 않는다.
- 007: ID가 있는 전체 예시 콘텐츠·portrait 자산 연결, 실제 일차/분기 편성, 세션과 적용 이력 저장.

샘플은 `Docs/DocumentContractExamples.json`이다. 네 인물 원본, PDF 대표 정답 두 쌍, 다섯 수정 지시를 담는다. 대표 문장만 수록한 **콘텐츠 계약 예시**이며 Resources 로딩이나 출시 일차에 연결하지 않는다. 복수 정답은 Answers 배열에 서로 다른 ID 쌍을 추가해 표현한다. 실행 검증용 테스트 데이터가 아니다.
